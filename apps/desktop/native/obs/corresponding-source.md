## Rebuild and audit

Follow the [native Windows build instructions](../../../../docs/screen-sharing-handoff.md#build-and-package-the-windows-sender). Keep the unsigned installer digest, inventory and import report together. The OBS C++ runtime and plugins are built from source using verified upstream OBS dependency binaries. Reconstructing the upstream OBS dependency binaries from their original sources is a separate release task.

Electron 45.1.0 and its Chromium components are outside `resources/obs-screen`, including the separate Electron `ffmpeg.dll`. Preserve their upstream notices with the full installer. [Electron 45.1.0 source and release](https://github.com/electron/electron/releases/tag/v45.1.0)

## Reduced FFmpeg candidate

The audited Windows OBS build enables external x264, GPL and version 3. It omits `--enable-nonfree`. OBS NVENC and the OBS x264 plugin expose their own H.264 encoders. The AMF texture encoder uses the separately linked AMD SDK inside the FFmpeg module. The same module still imports the FFmpeg libraries for output, source and muxing features. A reduced FFmpeg build must retain the module's required function exports and supported encode paths.

Use [build-ffmpeg-candidate.sh](build-ffmpeg-candidate.sh) with the exact n8.1.2 source archive inside a disposable Linux builder. The script uses mingw-w64, GCC, Make, binutils, NASM and xz, and preserves the configure output, license files and DLL digests. This profile disables GPL and nonfree code and external x264 in FFmpeg. The OBS x264 module and its own dependency are still required. Verify the candidate's exported ABI against each importing OBS binary, then test capture, software fallback, NVENC and physical Radeon AMF against its exact Windows DLLs before changing the installer. The pinned OBS runtime remains the release candidate's source of FFmpeg DLLs.

The current source collection is a draft. Independently reconstructing the full upstream dependency inputs, including all static FFmpeg dependencies, and rebuilding from the proposed archive remain required. Rajcord's own MIT-licensed files retain their MIT notices. For the stock-linked helper, GPLv3 is the plausible combined-work route because libobs's GPL-2.0-or-later grant allows choosing v3 and the actual FFmpeg DLLs require v3 or later. The reduced candidate removes that FFmpeg configuration constraint. Review all other linked grants, including GPL version restrictions, Apache-2.0 and the native SDK terms. The release decision must cover the helper's combined-work distribution terms and whether the Electron app's dedicated IPC, lifecycle and authorization coupling requires including the app within that scope. Define the actual corresponding-source delivery, notices, user relinking terms where applicable and codec rights before distribution. [GPLv3 source and aggregation terms](https://www.gnu.org/licenses/gpl-3.0.html) · [FSF FAQ on separate programs](https://www.gnu.org/licenses/gpl-faq.html#MereAggregation) · [FFmpeg distribution guidance](https://ffmpeg.org/legal.html)

The separately built coturn image is absent from the Windows payload. Its Dockerfile pins the 4.19.2 source archive and Debian base. Keep the coturn license, Rajcord's refresh-cap patch and the actual Debian package notices with its own distribution.
