# Dedicated TURN for Rajcord screen sharing

The screen API can issue 60-second TURN REST credentials using a dedicated coturn secret. Direct P2P stays preferred through normal ICE candidate selection. Coturn carries fallback traffic, including when both peers use allocations on the same server. LiveKit continues to own voice and its embedded TURN policy. The legacy screen relay selection remains available for rollback. The screen feature runs on the existing authenticated voice binding and checks that binding before issuing or renewing credentials.

## Local qualification

On Windows, build with `pnpm desktop:obs:setup` and `pnpm build`. Run `pwsh -NoProfile -File scripts/test-screen-coturn.ps1 -Extended -Long` with Docker Desktop and OpenSSL. The fixture generates a one-day localhost certificate and a random secret. It publishes only loopback listener ports, runs coturn and the owned Electron media fixtures, and tears down its containers and keys. The relay advertises its private fixture bridge address and accepts peer permissions only for that address. The host configuration has a separate destination policy. The harness stops on a new Windows Audio failure and verifies the authorized tone after ICE restart and rejoin. `-Long` checks media past the original allocation lifetime, records the container interface transmit byte delta over the one-viewer run, and confirms that the allocation gauge returns to zero after disconnect.

The Windows helper uses libdatachannel with the pinned libnice ICE backend and OpenSSL. Native TURN over UDP and TCP uses libnice. For publisher TURN/TLS, Electron main establishes a TLS 1.2+ connection with certificate and hostname verification, then forwards the authenticated TURN stream through a loopback TCP endpoint. Each endpoint uses an ephemeral port, bounds connections and belongs to one viewer. It closes with the viewer, the ICE generation or the helper. Remote peers receive ICE relay candidates. Browser clients use their own TLS implementation. TURN/TCP and TURN/TLS refer to the client-to-relay transport. The relay allocations carry UDP. [Native build inputs](screen-sharing-handoff.md#build-and-package-the-windows-sender) · [Coturn 4.19.2 options](https://github.com/coturn/coturn/blob/4.19.2/examples/etc/turnserver.conf)

The rebuilt NVENC package selected relay/relay on each forced UDP, TCP and TLS test and decoded H.264 and Opus with zero packet loss. Normal ICE selected host/host with TLS offered. A four-second relay interruption stopped decoded frames and a fresh ICE generation restored media in about 874 ms. Three local viewers sampled 6.48% coturn CPU and 8.74 MiB RAM. The 135-second one-viewer UDP test decoded 8,129 frames and 1.63 MB of Opus with no RTP loss. The allocation gauge reached zero in 118 seconds after disconnect. Across the 142.16-second fixture interval including setup and rejoin, the relay interface sent 39,096,314 bytes, about 2.20 Mb/s or 0.99 GB per viewer-hour. The fixture configured 2 Mb/s video. The 12 Mb/s WAN planning case remains open.

Earlier native candidate builds passed forced UDP, TCP and publisher TLS with guarded PCM and rejoin. The standalone installer passed all three local video relay paths plus the 135-second UDP allocation-refresh test. In this run, allocation metrics returned to zero 100 seconds after disconnect. The TLS case exercises the publisher tunnel and the browser's UDP relay leg. For a local video-only run, pass `-VideoOnly` to the coturn fixture. WAN acceptance uses the separate procedure below. ## Production preparation

This procedure requires approval for the host changes and the reviewed application release. The read-only survey found 2 vCPUs, 3,915 MiB RAM with 2,384 MiB available, 28 GB filesystem space available, and no listeners on the planned new ports. The Docker daemon reported standard AppArmor/seccomp and no user-namespace remapping. `nft` is available and the WAN interface was `eth0`. Refresh these checks at execution time.

1. Reserve a dedicated DNS-only IPv4 hostname such as `screen-turn.rajcord.com`. Use the VPS's assigned public IPv4. Confirm it is present directly on the host with `ip -4 address show`. The supplied host configuration expects a directly assigned IPv4. A NATed VPS requires reviewed address mapping and a separate hairpin test. Reserve TCP/UDP 3479, TCP 5350 and UDP 52000–52063. Verify no collisions with `ss -lntup` and with the current container port mappings. Keep LiveKit's 3478, 5349, 7881, 7882 and 50000–50199 assignments.
2. Provision a dedicated trusted certificate for the screen hostname with the existing ACME procedure. Prepare a private config directory such as `/etc/tricord/production/screen-turn`, outside the checkout, root-owned and group-readable by the reserved container GID 61628. Verify `getent passwd 61628` and `getent group 61628` before reserving the IDs. Install the PEM pair as `fullchain.pem` and `privkey.pem` with mode 0640, owned by root and group 61628. Treat the resolved private key as secret. Certificate renewal must replace the pair atomically before restarting only the coturn container. Nginx continues to handle application HTTPS. TURN TLS terminates in coturn on 5350.
3. Build the private runtime configuration from `infrastructure/screen-turn/turnserver.common.conf` plus `turnserver.host.conf.template`, substituting the verified hostname and IPv4 for both placeholders. Append `static-auth-secret=` with a new value generated by `openssl rand -hex 32`. Keep this config at mode 0640. Configure the same value as `SCREEN_COTURN_SECRET` in the root-only Rajcord `app.env`, with `SCREEN_COTURN_HOST` set to the certificate hostname. Prepare the file change for the approved deployment. Retain the previous `SCREEN_TURN_HOST` for rollback. Application and relay credentials stay out of the image and logs.
4. Verify firewall and Docker scope before listening. Validate the dedicated rules with `sudo nft -c -f infrastructure/screen-turn/egress.nft`. After authorization, load the dedicated table and register it with the existing firewall's persistence mechanism before starting coturn. It permits the reserved UID's same-host UDP relay traffic only to the reserved relay port range and denies other local, private, link-local, metadata, special-use and IPv6 destinations. Coturn also enforces its IPv4 peer deny ranges, authentication, per-user and global allocation limits. Reserve the entire relay range for this service. Verify the UID applies to the real socket owner in the host namespace. Add ingress permits for UDP/TCP 3479, TCP 5350 and UDP 52000–52063 on the verified WAN interface using the existing host firewall procedure. Keep 9641 on loopback.
5. Export `SCREEN_TURN_RUNTIME=/etc/tricord/production/screen-turn`. Run `docker compose -f infrastructure/screen-turn/compose.host.yaml config --quiet`, then use the approved host procedure to build and start the distinct coturn project with `docker compose -f infrastructure/screen-turn/compose.host.yaml up -d --build`. BuildKit checks the pinned Coturn 4.19.2 source digest. The small local patch applies the configured allocation cap after normalizing an omitted or sub-minimum lifetime. The service runs with no capabilities at UID 61628, a read-only root filesystem, 256 MiB memory, one CPU and capped logs. Check container status and `curl --fail http://127.0.0.1:9641/metrics`. From a separate network, validate certificate hostname and chain with `openssl s_client -connect screen-turn.rajcord.com:5350 -servername screen-turn.rajcord.com -verify_hostname screen-turn.rajcord.com -verify_return_error`.
6. Use the reviewed Rajcord deployment once the relay and firewall checks pass. Repeat with two authorized accounts on separate networks. Confirm direct ICE first, then force one and both peers through relay. Verify decoded video, audible scoped audio, restart and cleanup, and existing LiveKit voice. Record relay use and WAN loss, latency and FPS. Test that same-host relay peers receive media while an unauthorized allocation and unsafe peer permission fail. Test restrictive networks where the destination ports are permitted. TLS on 5350 does not provide fallback on networks that permit only TCP 443.

### WAN acceptance

**Not Yet Verified.** Run the following against approved staging with a Windows OBS publisher and a viewer on physically independent internet connections. Add one or two viewers and repeat with Edge as the supplemental viewer. An unpackaged desktop build can target the exact staging HTTPS origin by setting `TRICORD_SERVER_URL`, clearing `TRICORD_DEV_URL`, and running `pnpm --filter @tricord/desktop exec electron .` after building. In the browser viewer, open `edge://webrtc-internals` before joining. Record the selected candidate pair's types, protocol, and relay protocol when available, along with decoded-frame, received-audio and packet-loss counter deltas. Confirm desktop receiver media and use the dedicated relay session counters to corroborate transport. An allocation by itself does not prove selection.
2. Measure an unrestricted direct run. Then use an authorized test-network gateway policy that blocks direct peer media and permits only one staging TURN listener at a time, with signaling, DNS and voice still reachable. Test TURN/UDP on 3479, TURN/TCP on 3479, then TURN/TLS on 5350. First constrain one client, then both. Confirm selected relay pairs and real decoder/tone results for each. Record whether restrictive conditions allow the configured port.
3. Interrupt the selected relay path for four seconds and restore it. Confirm changed ICE credentials, elapsed time until moving video and tone resume, and working voice. Hold a media run for at least 135 seconds to cross the initial allocation lifetime and track renewal. Revoke the viewer, try a separate allocation with expired credentials, then repeat with publisher Stop and source closure. Confirm media stops and allocation count returns to its pre-test level after the configured expiry.
4. At one and three viewers, sample staging WAN-interface outbound bytes at the start and after at least five minutes of stable relay playback. Subtract the idle rate for the same interval. Compute viewer-hour egress as `(outbound byte delta − idle bytes) × 3600 / seconds / 1e9 / viewers`. Record the measured video bitrate, coturn CPU, memory and allocation count alongside provider counters. Compare the measured result with the 5.4 GB/hour planning estimate at 12 Mb/s.

## Capacity and monitoring

The initial limits are 12 allocations per stable account key, 48 total, a 64-port relay pool, 120-second allocation lifetime, 1.75 MB/s per allocation and a 36 MB/s reservation ceiling. Coturn reserves the per-allocation limit during ICE gathering. Three links can temporarily use eighteen allocations when both peers gather all three transports, which reserves 31.5 MB/s before any media flows. The client may create more than one allocation while gathering ICE. The user quota groups renewed usernames by their stable opaque suffix. A revoked session stops receiving new credentials and the app closes its links. A credential already copied from a session remains usable for new allocations until its timestamp expires. Existing allocations follow coturn's refresh and expiry rules.

At 12 Mb/s a continuously relayed viewer uses about 5.4 GB/hour of outbound WAN transfer and roughly the same inbound, before overhead. Three such viewers are about 16.2 GB/hour outbound or 32.4 GB/hour combined. A same-node relay-to-relay hop stays on the VPS. Check how the provider counts ingress and egress and compare the sustained test to its monthly allowance before approving rollout. Capture actual container CPU, memory and network I/O with `docker stats --no-stream`. Scrape `127.0.0.1:9641/metrics` locally for `turn_total_allocations`, traffic bytes and rate-limit counters, check allocation denials in the service logs, and compare with WAN-interface/provider counters. Keep username labels off. Record an alert threshold against the verified plan and monthly budget. [Coturn monitoring reference](https://github.com/coturn/coturn/blob/4.19.2/docs/Prometheus.md)

## Rollback

Remove the two `SCREEN_COTURN_*` settings from the active API runtime and recreate only the app service through the existing approved deployment with its previously tested image and configuration. Verify readiness, direct screen media and LiveKit voice. Stop the dedicated relay with `docker compose -f infrastructure/screen-turn/compose.host.yaml down`. Remove only the ingress rules added for this relay and delete the dedicated nftables table with `sudo nft delete table inet rajcord_screen_turn` after coturn stops. Retire the corresponding persistence entry and DNS/certificate only if they are no longer in use. Preserve the established voice and app networks, existing secrets, database, and prior rollback evidence.
